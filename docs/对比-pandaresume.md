# 对比：pandaresume.cn 的「AI 简历打分」 vs 我们的 resume-reviewer

> 调研日期：2026-11-09　调研方式：静态逆向 22 个前端 chunk + 真浏览器跑通打分 + 读回服务端返回的 JSON
> 对照样本：同一份简历（产品运营经理，695 字）+ 同一份 JD（182 字），两边各跑一次

---

## 1. 我们是怎样把它的打分发问出来的

站点是 Next.js + Turbopack，`/zhenduan/` 页面 58,637 字节，前端 chunk 22 个、合计约 1.4 MB。真正有用的只有 3 个：

| chunk | 里面是什么 |
| --- | --- |
| `0votk5_cfyv9g.js` | API 客户端：`fetch(base+path, {credentials:"include"})`，所有请求带 `X-Fingerprint` |
| `38r_ax1to21ht.js` | `/ai/score-resume`、`/ai/parse-file`、`/ai/import-resume`、`/ai/optimize-resume-stream` |
| `3pob3zub2rj_j.js` | `/resume-scores`、`/target-positions` 的增删改查 |

打分的调用只有一行：

```js
scoreResume({ resume_id: j.id, position_id: w.id })
```

**只传两个 ID，不传正文。** 简历正文和 JD 在做「导入」「新建目标岗位」时就已经存进它的库了，所以 prompt、模型、温度、权重全部在服务端，客户端一行都看不见——这一点决定了：它的打分**不可在本地复算**。

### 指纹校验

服务端要 `X-Fingerprint` 头，值就是 `localStorage.FingerPrint`（32 位 hex）。缺了直接：

```json
{"code":104,"message":"缺少浏览器指纹","data":null}
```

所以直接 `curl` 打接口是打不通的，必须借浏览器上下文（页面里 `fetch` 时手动补这个头）才读得回数据。

### 匿名额度只有一次

第一份简历 + 第一个岗位，匿名就能评出一份 85 分的完整报告。第二份再点「开始简历打分」，**页面没有任何反应**：没有 toast、没有遮罩、没有网络请求——源码里是

```js
if (!await m([PrivilegeAIDiagnose])) return void k(!1)
```

权限没过就静默 return。用户看到的是「按钮点了没反应」。

## 2. 它到底怎么打分（有返回 JSON 为证）

`GET /api/resume-scores/2860` 拿回来 7,969 字节，结构如下：

```json
{
  "id": 2860, "resume_id": 253260, "resume_name": "李雷的简历",
  "target_position_id": 6779, "target_position_name": "产品运营经理",

  "language_expression_score": 88,
  "language_expression_details": [{ "title": "语言清晰度", "comment": "- **优点**：…\n- **不足**：…\n- **改进建议**：…" }, …],

  "information_completeness_score": 78,
  "information_completeness_details": [ … ],

  "content_relevance_score": 86,
  "content_relevance_details": [ … ],

  "professionalism_score": 86,
  "professionalism_details": [ … ],

  "overall_score": 84.5,
  "overall_comment": "## 优势\n- …\n\n## 不足\n- …\n\n## 建议\n- …",
  "created_at": "2026-11-09T16:59:27+08:00"
}
```

### 总分公式：四个维度等权平均

```
overall_score = (88 + 78 + 86 + 86) / 4 = 84.5
```

存的是 84.5，页面显示 **85**，等级「优秀」。页面自己写着「**综合四个维度的平均结果**」——这就是全部公式，没有权重、没有门槛、没有分段。

### 四个维度，各管一段，互不重叠

| 维度 | 实测分 | 细项（每个细项都是一段「优点/不足/改进建议」） |
| --- | --- | --- |
| 语言与表达 `language_expression` | 88 | 语言清晰度、逻辑结构、专业术语使用、表达简洁性 |
| 信息完整性 `information_completeness` | 78 | 基本信息、工作经历、项目经历、教育背景、技能证书 |
| 内容相关性 `content_relevance` | 86 | 技能匹配度、经验相关性、行业背景、岗位适配性 |
| 简历专业性 `professionalism` | 86 | 整体结构、内容质量、格式规范、亮点突出 |

17 个细项，每个细项的 `comment` 都是固定三段：**优点 / 不足 / 改进建议**，且都引用了简历原句（例：「次日留存从31%提升至44%」）。

### 输入与输出

- **输入**：简历文件（docx/pdf 解析后入库）+ 岗位（`position_name` / `company_name` / `job_description` / `job_source`）。页面文案自述流程是「结构体检 → 内容匹配 → 综合评分」，并宣称「多维度模型深度解析」「专业HR视角校准」。
- **输出**：一个页面：综合得分 + 等级 → 四维条形图 → 综合评价（优势 4 条 / 不足 4 条 / 建议 6 条）→ 维度建议（17 个细项）。
- **不输出**：没有「改哪一句」的可执行补丁，没有改完重评，没有版本历史，没有下载件，没有 ATS 判读，没有面试追问。

## 3. 同一份简历、同一份 JD，两边各跑一次

| | pandaresume | 我们（resume-reviewer v2.6.2） |
| --- | --- | --- |
| 总分 | 84.5 → 显示 **85 · 优秀** | **64**（通用）/ **65**（互联网科技 · 可投） |
| 维度 | 4 个 0-100 分：88 / 78 / 86 / 86 | 5 个 1-5 分：岗位对口 4 / 结果与影响 4 / 证据质量 3 / 结构 2 / 竞争力差异 2 |
| 权重 | 等权 25% × 4 | 25/25/20/15/15；选行业后按行业档案改权重（互联网：25/28/20/12/15） |
| 等级 | 优秀（只观察到这一档） | 可投 / 勉强 / 待改 + 初筛门 + 面试门 |
| 报告体量 | 页面一屏 + 17 个细项 | 3,102 字 Markdown，7 个小节 |
| 门槛 | 无 | `pass_min=65`、`interview_min`、硬阻断（编造数字、隐私字段） |
| 不可判 | 没有这个状态，每维都必须给分 | ATS 7 平台 × 三态，判不出就写 `? 判不出` |
| 改稿 | 只给建议 | 补丁 + 写入前守卫 + 重评 + 显式报差 + 撤回 |
| 复算 | 不可能（prompt 在服务端） | 规则引擎可本地跑，`/rules` 把公式与阈值公开 |
| 测试 | 无（前端 0 测试） | 28 套件 / 588 断言 |

> 分数不能横向比：它的 85 和我们的 65 是两把不同的尺子。能比的是**方法**。

## 4. 方法差异，逐项对照

| 维度 | pandaresume | 我们 |
| --- | --- | --- |
| 分是怎么来的 | 4 个 0-100 分取平均 | 5 个 1-5 整数分 × 权重 × 20 |
| 权重 | 固定等权 | 可在 `config/rubric.yaml` 配，11 个行业档案 |
| 维度分粒度 | 每个细项一段评语，但细项分不单独给 | 每维一个分数 + 一句可核的算分依据（如「12 条经历里 12 条带结果信号」） |
| 分数可手算 | 只有平均那一步 | 全程可手算，报告里直接印「计分口径」 |
| 判断不了时 | 照给分 | 写 `? 判不出`（ATS），或直接不给分（<120 字转建议模式） |
| 分数与改稿 | 断开 | 补丁落盘即重评，报 `+3 / −2` 并说明原因 |
| 可回退 | 无 | 版本链（上限 10 个），可撤回 |
| 可复核 | 无规则公开、无测试 | `/rules` 公开全部阈值；588 断言钉住每个数字 |
| 隐私 | 把「没写性别/出生日期/意向薪资/头像」算进扣分 | 隐私字段不进任何维度（`test_privacy_words_never_score`） |
| 成本 | 每份简历一次模型调用（服务端付费），匿名 1 次 | 规则引擎 0 成本；要语义改写才用自己的 key |
| 失败处理 | 权限不过=静默无反应 | 明确报错给下一步（`TEXT_TOO_SHORT` / `CHAT_FORMAT` / 重试一次） |

## 5. 它确实做得比我们好的四件事

1. **细项颗粒度更细，且结构统一。** 每维固定 3-5 个细项，每个细项都是「优点 / 不足 / 改进建议」三段。我们的维度评语只有一行（「12 条经历里 12 条带结果信号」），可核但对求职者不够「可执行」。
2. **维度名用的是 HR 词汇。** 「语言与表达 / 信息完整性 / 内容相关性 / 简历专业性」——不看文档也知道在说什么。我们的「证据质量 / 竞争力差异」是评审术语，第一次看要猜。
3. **综合评价的条数多。** 优势 4 条、不足 4 条、建议 6 条，每条都点名到具体句子。我们是 3 条改写 + 3 条追问，覆盖面窄。
4. **单页一站式。** 导入 docx → 建岗位 → 出报告，全程不跳页，认知负担低。我们有评审页 + 工作台两个页面，中间还要选引擎。

## 6. 我们比它强的地方（都可当场验证）

- **权重能解释、能调。** 它等权，于是「语言表达 88 分」把总分拉到 84.5——一个运营岗最该看的「岗位匹配」只占 1/4。我们的总分公式印在报告第二行，换行业换权重，分数跟着变（实测同一份简历：通用 64 / 互联网 65 / 金融 62 / 国企 60 / 设计 55）。
- **分数段先定段、再定分。** 5 档（90-100/80-89/65-79/50-64/<50）写死了「长什么样、典型画像、最常见误判、建议分」，prompt 与 `config/rubric.yaml` 逐字对齐，改一处测试就红。
- **判不出就说判不出。** ATS 七个平台（北森、Moka、智联、51job、实习僧、猎聘、Workday）每条检查只有 `✓/✗/?` 三态；正文里看不到版面就写「判不出：版面在正文里看不到」。它没有这个状态——78 分的「信息完整性」里 5 个细项全是主观判断，没有一条可核证据。
- **面试视角。** 追问四件套：他会问的那一句 / 怎么准备 / 答错的样子 / 风险等级。它完全没有。
- **闭环。** 改完立刻重评并报差，版本可撤回，编造数字在**写入前**就被拦（不是在报告里事后提醒）。
- **可复核。** `/rules` 页把公式、阈值、行业权重、分数段、ATS 清单全部公开；588 条断言保证「配置改了文档就红」。它 0 测试、0 规则公开。
- **不填 key 也能用。** 规则引擎离线出分（v2.6 起工作台同样支持）；它必须登录且匿名只有 1 次。

## 7. 它的三个硬问题（都有 JSON 原文为证）

**① 把「不写性别/出生日期/意向薪资/头像」当成缺点扣分。**

`information_completeness_details[0]`（基本信息）原文：

> **不足**：个人信息维度较为单一，缺少性别、出生日期、政治面貌等常见字段；未提供微信、GitHub 等补充联系方式；头像未上传，可能影响简历完整度；意向薪资未填写…
> **改进建议**：建议补充性别、出生年月等基础信息…上传职业化头像提升简历专业感…

在当下国内求职语境里，性别/出生日期/政治面貌/头像属于**不建议主动提供**的信息（招聘方收集还有合规风险）。一个打分工具把它算进「完整度」并建议补上，是在教用户填无用甚至有害的信息。我们的做法相反：隐私字段既不加分也不扣分，只提示「可以删」。

**② 等权平均掩盖了岗位匹配。**

四个维度各 25%。实测这份简历「语言与表达 88」，比「内容相关性 86」还高，而岗位最关心的「会员体系/GMV/复购」缺口，被平均稀释成「不足」里的一条文字。换成一个权重可配的模型，同样四维数据能拉开 10 分以上差距——这就是我们做行业权重的原因。

**③ 没有「判不出」。**

17 个细项全部必须给结论，没有一条写「这条我看不出来」。对求职者的实际伤害是：分低了不知道为什么低，也不知道哪条是猜的。

**④（体验）第二次打分静默失败。** 按钮点下去没反应、没提示、没请求，用户只会以为网站坏了。

## 8. 值得抄的三件事，以及不抄的三件事

**建议做（按性价比排）**

| 优先级 | 做什么 | 怎么落 | 成本 |
| --- | --- | --- | --- |
| P1 | 每个维度给 3-5 个**固定细项**，每个细项「优点 / 不足 / 改进建议」三段 | `config/rubric.yaml` 加 `details:`；`review.py` 渲染；补 6-8 条断言 | ~2h |
| P2 | 报告头部加**中文等级**（优秀 / 良好 / 合格 / 待改） | `verdict` 已有，加映射即可 | ~30min |
| P3 | 维度名换 HR 词汇（证据质量→「经历可信度」，竞争力差异→「亮点突出度」） | 只改 `rubric.yaml` 的 `label`，但会动 prompt 表格与 3 处测试 | ~1h |

**明确不抄**

- **等权平均**：省事，但把「岗位匹配」压成 1/4，与产品目标冲突。
- **把个人信息当完整度**：既过时又有合规风险。
- **没有 unknown 状态**：宁可少说，也不能编一个分数。

## 9. 顺手抓到我们自己的一个真缺陷（已修）

做这次对照时，同一份 JD 喂给我们，报告里出现了：

```
**关键词覆盖 20%**
- ❌ **岗位职责**：简历里完全没有
- ❌ **负责会员体系与用户增长**：简历里完全没有
- ❌ **制定季度运营策略并对**：简历里完全没有
```

根因：`scripts/local_engine.py::_jd_match()` 按标点切完就当关键词用，中文 JD 的整句（甚至小标题「岗位职责」）直接进了词表，长句还被 `12` 字截断成「制定季度运营策略并对」。

改法：`_jd_terms()` 三层削——①按标点切句；②按「与/和/及/或」拆并列；③反复削掉开头动词（负责/熟练/掌握/包含…）、句中动词前缀、结尾连词（并对/并且/的/等）。同时加了 23 个停用词（岗位职责/任职要求/加分项…）与纯动词过滤。

同一份 JD 的效果：

| | 改前 | 改后 |
| --- | --- | --- |
| 关键词 | 岗位职责、负责会员体系与用户增长、制定季度运营策略并对、GMV… | 会员体系、用户增长、季度运营策略、GMV、用户分层、召回机制、留存、复购、产品、数据团队协作 |
| 覆盖率 | 20% | **50%** |
| 报告里的废提示 | 「❌ 岗位职责：简历里完全没有」 | 消失 |

新增 2 条断言（`test_jd_terms_are_terms_not_clauses`、`test_jd_coverage_on_chinese_prose`），全量 **28 套件 / 588 断言**。

---

## 10. 一句话结论

**它是一份写得很好看的体检报告，我们是一套可以复核的评审流程。**
它的四维细项值得抄，它的等权、把个人信息算进完整度、没有「判不出」，一样都不该抄。
