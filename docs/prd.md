## 0. 一句话

**上传一份简历，50 秒后拿到一页能改的报告：结论 + 3 条可执行改写 + 1 个今天就能做的动作。**（事实已确认的改写可直接复制；需确认或待补数字的只展示，不进入复制区。）

## 1. 产品目标与使用场景

### 1.1 目标

| 层级 | 目标 | 判断方式 |
|---|---|---|
| 业务目标 | 让找第一份实习的学生知道**哪句话会让他被筛掉**，并且当场能改 | 用户改完能说出"我改了哪 3 句、为什么" |
| 用户目标 | 不看长篇分析，10 分钟内完成一轮修改 | 报告页停留时间 < 10 分钟且产生 1 次以上复制/下载 |
| 非目标 | **不是**"帮你把简历写漂亮"，**不是**"保证拿到面试" | 明确不输出通过率、不做代写 |

### 1.2 用户

**唯一目标用户**：大二～大四、找第一份实习的本科生，或研一找日常实习的研究生。

特征（决定了产品形态）：

- 多数没有正式实习，简历主体是课程设计、竞赛、兼职、社团；
- 不知道企业筛选是怎么发生的，以为"写详细一点"就有用；
- 一份简历投几十家，改一次用一季 —— **决策周期 10 分钟，不是 10 天**。

### 1.3 核心场景

| # | 场景 | 用户带着什么来 | 期望拿走什么 |
|---|---|---|---|
| S1 | **投递前自检** | 一份写好的 PDF | 现在能不能投；如果不能，改哪一句 |
| S2 | **被拒后复盘** | 投了 20 家没回音 | 到底是简历问题还是岗位不匹配 |
| S3 | **同学互评** | 室友的简历 | 一份客观的第三方意见，不是客套话 |
| S4 | **换方向改简历** | 同一段经历投不同岗 | 这份简历对**这个**岗位够不够 |

### 1.4 明确不做（非目标）

| 不做 | 原因 |
|---|---|
| 代写/生成简历正文 | 虚构风险，且用户需要的是判断不是文案 |
| 预测通过率、offer 概率 | 无法预测，给数字就是编造 |
| 评价长相、性别、年龄、籍贯、学校层次 | 与投递决策无关 |
| 在线编辑器 / 模板排版 | 那是另一类产品（模板站），不是本产品的价值点 |
| 账号体系、云端历史 | V1 验证的是"判断准不准"，不是"用起来方不方便" |

### 1.5 成功指标

| 指标 | 目标 | 现状 |
|---|---|---|
| 单份评审耗时 | ≤ 120 秒（1 次） | 实测 49~110 秒 |
| 单份成本 | 可接受 | 约 25k 输出 token（推理模型） |
| 引用可追溯率 | 100% | 197/197（8 份真实简历） |
| 编造数字 | 0 | 0 |
| 用户完成一次修改 | ≥ 1 处 | **未验证（无真实用户）** |
| 独立人工评分一致性 | 需双人盲评 + heldout | **工具已就绪，独立标注 0 份** |

> ⚠️ 最后两行仍是这套产品最大的空白：**判断准不准，已经没有借口用“测试通过”代替，但独立人工数据还没采。**

### 1.6 人工验证状态（阶段 D）

| 项 | 现状 |
|---|---|
| 数据集 | 8 份，全部 development；目标 60 份 |
| 独立标注者 | 0 / 2 |
| 双人共同标注 | 0 / 60 |
| heldout | 0 / 18 |
| 模型意见/改写审阅 | 0 份 |
| 重复评审 | 0 组 |
| OCR 对照 | 0 组 |
| 旧版单人非盲 gold | 4 份，仅探索性代理，不能当准确度 |

工具：`scripts/human_eval.py`；方案：[人工评测方案.md](人工评测方案.md)。数据未达门槛时报告固定输出 `not_ready`，不写“准确率”。

## 2. 整体页面结构与视觉设计要求

### 2.1 信息架构：单页三步，无路由

```
┌─────────────────────────────────────────┐
│  标题 + 一句话说明                        │
├─────────────────────────────────────────┤
│  [网络自检横幅]（异常时才出现）            │
├─────────────────────────────────────────┤
│  步骤 1 · 上传                            │
│   ┌───────────────────────────────┐     │
│   │  上传文件 │ 粘贴文本   （Tab） │     │
│   │  [拖拽区 / 文本框]             │     │
│   │  [下一步]                      │     │
│   └───────────────────────────────┘     │
├─────────────────────────────────────────┤
│  步骤 2 · 确认（步骤 1 完成后才出现）      │
│   类型徽章 · 字数                          │
│   [提取文本预览，最多 600 字]              │
│   目标岗位 [输入框]                        │
│   评审次数 [1 次 / 3 次取中位]             │
│   [开始评审] [换一份]   等待计时            │
├─────────────────────────────────────────┤
│  报告区（评审成功后出现并滚动到视野）        │
│   结论 / 排版问题 / 三处改写 / 一个动作     │
│   / 投递前核对 / 提示                      │
│   [复制报告] [下载 .md] [再来一份]         │
├─────────────────────────────────────────┤
│  页脚：隐私说明 + 边界说明                 │
└─────────────────────────────────────────┘
```

**不做多页、不做侧边栏、不做导航**。理由：一次会话只有一个任务，任何额外可点击元素都是干扰。

### 2.2 布局与尺寸

| 项 | 规范 |
|---|---|
| 内容最大宽度 | `820px`，水平居中 |
| 页面内边距 | 上 36px，左右 20px，下 80px |
| 卡片 | 白底、1px 边框 `#e5e7eb`、圆角 12px、内边距 22px、卡片间距 16px |
| 拖拽区高度 | 约 130px（padding 38px 20px） |
| 报告预览框最大高 | 220px，超出内部滚动 |
| 文本域最小高 | 180px |

### 2.3 视觉规范

| 用途 | 值 |
|---|---|
| 背景 | `--bg: #f6f7f9` |
| 卡片 | `--card: #ffffff` |
| 正文 | `--ink: #1a1a1a`，15px / 行高 1.7 |
| 次要文字 | `--muted: #6b7280`，13~13.5px |
| 主色（按钮、强调） | `--accent: #2563eb` |
| 主色浅底 | `--accent-weak: #eff6ff` |
| 成功 / 警告 / 危险 | `#059669` / `#b45309` / `#dc2626` |
| 字体 | `-apple-system, "PingFang SC", "Microsoft YaHei"`，不引入外部字体 |
| 代码/等宽 | `ui-monospace, Menlo, Consolas`（用于引用原文） |

**设计原则**

1. **报告的"原文→改成"必须用等宽字体 + 浅灰底**，让用户一眼分清"这是简历里的字"和"这是我的建议"。
2. **不出现图表、雷达图、进度环**。用户要的是能抄走的句子，不是分数可视化。
3. **颜色只表达状态**（过/挂、正常/警告），不做装饰性用色。

### 2.4 状态设计（必须有明确视觉）

| 状态 | 表现 |
|---|---|
| 空 | 拖拽区提示"点击选择或把简历拖进来" |
| 已选文件 | 显示 `文件名 · 大小 MB`，按钮文案变为"开始识别" |
| 识别中 | 按钮禁用 + 文案"识别中…" |
| 识别成功 | 切到步骤 2，显示类型徽章与字数 |
| 评审中 | 按钮禁用 + 转圈 + **实时计时**"已用 N 秒（通常 40~120 秒）" |
| 评审成功 | 报告区渲染并 `scrollIntoView` |
| 评审失败 | 红色错误框，文案分两类（见附录 A） |
| 网络异常 | 顶部常驻横幅，说明是"没启动"还是"请求被打断" |

### 2.5 响应式

- 移动端：宽度 < 640px 时卡片内边距收窄至 16px，字号不变（不缩字，缩间距）。
- **不做移动端专属交互**。整页在手机上可用即可，不追求体验最优。

### 2.6 文案规范

| 规则 | 例子 |
|---|---|
| 说人话，不出现技术术语 | ❌ `fetch failed` → ✅「本地服务已经停止，请重新启动」 |
| 错误必须给出下一步动作 | ❌「上传失败」 → ✅「只提取到 12 字，可能是空白页，请换一份或直接粘贴文本」 |
| 不用感叹号，不卖萌 | — |
| 数字带单位 | "约 15 分钟"、"95% 的客户" |

## 3. 每个模块的具体功能和操作流程

### M1 · 输入模块

| 功能点 | 说明 |
|---|---|
| F1.1 文件上传 | 拖拽 或 点击选择；`accept` 限制为 8 种后缀 |
| F1.2 粘贴文本 | Tab 切换；占位符「把简历文字粘贴到这里…」 |
| F1.3 大小限制 | 前端不限制，后端 30MB 上限 |
| F1.4 文件回显 | 显示文件名与 MB |
| F1.5 合法性预检 | 粘贴文本 < 80 字 → 前端直接拒绝并提示 |

**支持格式**：`.pdf` `.png` `.jpg` `.jpeg` `.webp` `.docx` `.txt` `.md`

**操作流程**

```
选择文件 ──► 回显文件名 ──► [下一步] ──► POST /api/extract
                                        ├─ 成功 → M2
                                        └─ 失败 → 红框提示，停留在步骤 1
```

**边界与约束**

- 只接受单文件；多选时取第一个。
- 图片不做前端压缩，交由后端统一转 PNG 并限宽 1400px（控制 token）。
- 超过 30MB 直接拒绝，不做分片。

---

### M2 · 识别与脱敏模块

| 功能点 | 说明 |
|---|---|
| F2.1 路由判断 | 按后缀分流：txt/md/docx/文字型 PDF 直接抽；扫描型 PDF、图片走视觉模型转写 |
| F2.2 扫描件判定 | PDF 抽出的文本 < 120 字 → 判定为扫描件，渲染页面图后 OCR |
| F2.3 脱敏 | 手机号 / 邮箱 / 身份证 → `[xx已脱敏]`；出生日期只脱敏到年；学历与工作起止时间**保留** |
| F2.4 规范化 | 压缩连续空格、去掉纯项目符号行、统一换行 |
| F2.5 结果回显 | 类型徽章 + 字数 + 前 600 字预览 |
| F2.6 会话建立 | 生成 `session_id`，文本与页面图存内存，TTL 30 分钟 |
| F2.7 图像授权 | 文字型 PDF/DOCX/txt 默认不渲染页面图；扫描件/图片必须由用户显式勾选后才调用视觉模型；未同意时返回 `IMAGE_CONSENT_REQUIRED` |

**操作流程**

```
POST /api/extract {text|b64, allow_images}
  ├─ 有 text 字段   → 直接脱敏规范化（不涉及图片）
  ├─ 有 b64 字段    → 写入临时目录 → 按后缀分流
  │    ├─ .pdf   → PyMuPDF 抽文本
  │    │            ├─ ≥120 字 → 直接用；allow_images=false 时不渲染页面图
  │    │            └─ <120 字 → 需要页面图；未同意则拒绝
  │    ├─ 图片   → 未同意则拒绝；同意后转 PNG → 视觉模型转写
  │    ├─ .docx  → python-docx（含表格）
  │    └─ .txt   → 直读
  ├─ 文本 < 80 字 → 返回错误「可能是空白页」
  └─ 无论成功或异常，finally 清理上传临时目录
```

**边界与约束**

- 扫描件判定阈值 120 字（经验值）。
- 转写失败不重试（成本高），直接报错让用户粘贴文本。
- **OCR 每次结果略有差异**（1057~1089 字），这会影响最终分数，见 5.3。
- 页面图不做图像脱敏；文案必须明确告知可能包含姓名、照片、联系方式等未脱敏信息。

### M3 · 评审模块

| 功能点 | 说明 |
|---|---|
| F3.1 组装 prompt | 模板 v1.7 + 岗位 + 脱敏文本 + few-shot 样例，约 16k 字符 |
| F3.2 是否带图 | 默认不带图；必须同时满足“用户允许页面图”且本次勾选“额外检查排版”，才会附加 `image_url`，否则 `has_image=false` |
| F3.3 调用模型 | OpenAI 兼容接口，**不传 `max_tokens`**（见附录 C） |
| F3.4 多次采样 | `repeat` 1~3，取分数居中的那一整份；单次失败不致命 |
| F3.5 结构校验 | 19 个必填字段、量表范围、分数与 verdict 自洽 |
| F3.6 事实校验 | 引用逐字命中、改写不得新增数字、隐私不回显 |
| F3.7 规则校验 | 两关公式、展示力覆盖、动作优先级、格式 10 项、客观性三级 |

**操作流程**

```
[开始评审] ──► POST /api/review {session_id, job, repeat, visual}
   │
   ├─ 会话不存在/过期 → 「会话已过期，请重新上传简历」
   ├─ 模型调用 N 次（N=repeat，失败跳过）
   │    └─ 全部失败 → 「多次调用都失败了，检查网络或模型额度」
   ├─ 每份候选：schema → 确定性字段重算 → 事实/规则校验 → 局部条目清理
   ├─ 只从通过门禁的候选里取中位
   │    └─ 无合格候选 → 「结果未通过事实与结构校验」，不落盘、不入历史
   ├─ render(...) → 一页 Markdown 报告
   ├─ 落盘 reports/{name}-{review_id前12位}.md / .json / .txt / .docx
   └─ 返回 {report, score, verdict, gates, quality}
```

### M3.1 质量门禁（交付前必须通过）

门禁把问题分为三级：

| 等级 | 含义 | 处理 |
|---|---|---|
| `blocker` | 结构、核心引用、隐私或规则矛盾 | 整份候选不可交付，不展示分数/复制/下载，不写正常历史 |
| `filtered` | 单条改写新增数字、原句无法回指、单条问题不可执行 | 仅撤下该条，其余安全内容仍可交付 |
| `warning` | 可由代码修正的派生字段、非关键提示 | 修正并记录，不阻断 |

确定性规则：

- 总分与维度加权结果相差超过 ±2 时，由代码重算；
- 档位按最终分数重算；
- 两道闸门按维度与格式规则重算；
- JD 覆盖率按关键词证据重算；
- JD 关键词被误判为命中时，降级为不匹配，而不是让整份报告失败；
- `needs_user_confirm=true` 或含 `[待补充]` 的改写仍可展示，但**不得进入一键复制区**；
- repeat 只从合格候选里取中位，坏结果不能因“分数居中”被选中。

正式交付接口在无合格候选时返回 `code=REVIEW_VALIDATION_FAILED` 和最多 5 条结构化错误，前端保留用户输入并提示重试。失败结果不得覆盖同名旧报告。

**约束**

- `repeat` 服务端钳制在 1~3，防误触烧额度。
- 请求超时 600 秒；模型侧 `finish_reason=length` 会打印警告。
- 评审不缓存结果，同一份重跑会重新调用（保证可复现比省钱重要）。

### M4 · 报告模块

**报告固定结构（顺序不可变）**

| 区块 | 必填 | 内容 |
|---|---|---|
| 标题行 | 是 | `# 简历评审 · {文件名}` |
| 元信息 | 是 | 岗位 + 时间 |
| 结论 | 是 | `分数 / 100　档位`；多次评审时附 `（3 次：53/55/58，取中位）` |
| 状态行 | 是 | 初筛 ✅/❌ ｜ 面试 ✅/❌ ｜ 格式 ✅/⚠️/⛔ |
| 一句话总结 | 是 | 引用块，必须解释"为什么是这个档位" |
| **排版上要改的地方** | 有则不缺 | 视觉检查里 `ok=false` 的项逐条列 |
| **三处可替换写法** | 是（≥1，目标 3） | 每条：原来 / 改成 / 为什么 |
| **今天先做这一件事** | 是 | 第一条 `next_actions` + 预计分钟数 |
| 投递前自己核对 | 可选 | 最多 4 条 |
| 自检提示 | 可选 | 灰字一行，不影响阅读 |
| ⚠️ 不可直接使用 | 仅事实错误时 | 红框，列出硬错误 |
| 页脚 | 是 | 问题总数、待核数字数、处理说明 |

**硬性规则**

- 含**编造数字**的改写 **不得**进入"三处可替换"区，被撤下的以一行说明代替。
- `needs_user_confirm=true` 的改写（权属升级）必须带 ⚠️ 提示。
- 所有用户输入必须 HTML 转义后渲染。

**操作**

| 动作 | 行为 |
|---|---|
| 复制报告 | 复制 Markdown 原文到剪贴板，按钮变"已复制"1.5 秒 |
| 下载 .md / .docx | 按当前 `review_id` 下载，不按文件名查找 |
| 再来一份 | 回到步骤 1，清空全部输入、模式、预览、报告与请求状态 |

### M4.1 · 历史与状态归属

- 每份评审生成唯一 `review_id`，保存内容哈希与配置哈希；报告文件名带 `review_id` 前 12 位，同名简历不覆盖。
- 历史列表只返回摘要；`GET /api/report?id=…` 返回该 ID 自己的报告和脱敏原文。
- 历史、预览、下载、删除共用同一个 `review_id`，不会出现“打开 B 却看到 A 的原文”。
- 无原文的历史显示明确空态；超过 600 字可展开全文。
- 前端使用请求令牌 + `AbortController`：新建、换一份、打开历史或加载另一份历史时，旧响应不得覆盖新界面。
- 旧版按文件名保存的历史以 `legacy-*` 兼容，只保留每个名字最新报告并标注旧记录。
- “比上次 +N”只在内容哈希和配置哈希均一致时计算；否则提示不可比，`delta=null`。
- 历史抽屉在桌面与手机均可用，手机也可逐份删除。

### M4.2 · 改版前后对比

用户改完简历再传一次，是一份**新内容**（哈希必不同），走单独一节「和上一版比」：

| 功能点 | 说明 |
|---|---|
| F4.2.1 找上一版 | 在最近 40 份历史里按**脱敏正文相似度**挑选，不看文件名；相似度 < 0.62 视为两份不相干的简历，不做对比 |
| F4.2.2 分数对比 | 只有岗位/JD/模型/发图/评审次数**和规则版本**都一致才给分差；否则清空 `delta` 并写明具体原因 |
| F4.2.3 维度与门槛 | 5 个维度、两道关、格式结论逐项前后对照，只列真正变了的 |
| F4.2.4 文本差异 | 按行新旧对照，按段配对成"改写"，统计新增/删除/改写行数 |
| F4.2.5 建议落实 | 三态：看起来已改 / 原句还在 / 改成了别的写法；措辞明确标注为**文本比对推断**，不是模型判断 |
| F4.2.6 不重复 | 同一份内容重评（哈希相同）走"分数抖动"，不再叠一节空 diff |

边界：报告 JSON 读不到就不对比（不猜）；差异列表最多返回 200 条，统计数字保留真实值。

## 4. 数据保存、导出和恢复

### 4.1 数据分类

| 级别 | 内容 | 处理 |
|---|---|---|
| **敏感** | 手机号、邮箱、身份证、出生日期 | 文本中**发模型前**脱敏，落盘文本同样已脱敏；页面图不脱敏，需用户明确同意 |
| **一般** | 姓名、学校、公司、项目描述 | 文本不脱敏（评审需要）；可能随页面图发送 |
| **衍生** | 评审结论、分数、改写建议 | 可落盘 |

### 4.2 存储位置与生命周期

| 数据 | 位置 | 生命周期 | 是否入库 |
|---|---|---|---|
| 上传的原始文件 | 系统临时目录 | 成功或异常返回时立即删除 | 否 |
| 页面图（OCR/排版用） | 内存（会话） | 30 分钟；仅用户同意时保留 | 否 |
| 脱敏文本 | 内存 + `reports/*.txt` | 会话 30 分钟 / 本地磁盘直到用户删除 | 已 gitignore |
| 报告 Markdown | `reports/*.md` | 本地直到用户删除；云端临时实例可能随实例清空 | 已 gitignore |
| 完整 JSON | `reports/*.json` | 同上 | 已 gitignore |
| 历史摘要 | `reports/.history.json` | 只含 review_id、名字、时间、分数、岗位、内容/配置哈希；不含正文 | 已 gitignore |
| 批量评测结果 | `outputs/*.json` | 永久 | 已 gitignore |
| API Key | `.env` | 永久 | 已 gitignore |

**不做数据库**。理由：单机单用户，文件即存储；引入 DB 只增加部署成本。云端临时磁盘不能承诺长期历史。

### 4.3 导出

| 形式 | 触发 | 内容 |
|---|---|---|
| 页面复制 | 点"复制报告" | 完整 Markdown |
| 下载 | 点"下载 .md" | 完整 Markdown，文件名 `简历评审.md` |
| 磁盘留存 | 自动 | `reports/{文件名}-{review_id前12位}.md` / `.json` / `.txt` / `.docx` |
| 命令行 | `python scripts/review.py` | 屏幕打印 + 同样三份文件 |

**命名规则**：网页评审为 `reports/{安全文件名}-{review_id前12位}.{md|json|txt|docx}`，不覆盖同名文件；CLI 仍按源文件名输出，用于本地单次调试。

### 4.4 恢复

| 场景 | 恢复方式 |
|---|---|
| 会话过期（>30 分钟） | 重新上传；无自动恢复 |
| 页面刷新 | 无状态恢复（内存态），需重来 |
| 想重看报告 | 点历史条目，按 `review_id` 重新打开；本地也可直接打开对应文件 |
| 只想改排版不想重跑模型 | `python scripts/review.py 原文件 --from-json` |
| 换 prompt 版本重评 | `--prompt v1.6` |

**明确不做**：自动保存草稿、断点续传、账号体系。V1 的单次会话足够短（<3 分钟），恢复成本低于实现成本。

### 4.5 清理

- **删单份**：历史条目右侧 `×` → `DELETE /api/report?id=…`，删除该 `review_id` 的 `.md/.json/.txt/.docx/.raw.txt` 与历史摘要。
- **删全部**：`Remove-Item reports/* -Recurse`（连历史一起删）。
- 会话过期时清空内存中的文本和图片字节。

报告与批量结果没有自动清理定时任务，避免误删用户文件。

| 不做 | 原因 | 什么时候做 |
|---|---|---|
| 账号 / 登录 | 单机单用户，无必要 | 要做 B 端时 |
| 多用户账号与云同步 | 当前单用户；跨设备同步需要账号与数据库，属于另一阶段 | 要做多人/云端时 |
| 批量上传 | 单份 50 秒，排队体验更差 | 有明确批量需求时 |
| 在线编辑简历 | 是另一个产品 | 不做 |
| 移动端专属优化 | 能用即可 | 有真实移动端使用数据后 |
| 多语言 | 用户全中文 | 不做 |
| 队列 / 并发控制 | 单线程够用（`ThreadingHTTPServer`） | 多用户时 |
| 数据看板 / 图表 | 与"能改的那一句"无关 | 不做 |
| 自动清理定时任务 | 手动删即可 | 磁盘告警时 |

### 5.3 已知代价（不是缺陷，是取舍）

| 取舍 | 代价 |
|---|---|
| 用推理模型 | 单次约 25k 输出 token，成本是普通模型 10 倍 |
| 带页面图评审 | 比纯文本多约 1.5k token，但格式层才能真判 |
| 不做缓存 | 重跑就是重跑，但结果可复现 |
| OCR 不重试 | 转写失败要用户手动粘贴 |
| 分数不绝对 | 单次 ±5 抖动；`repeat=3` 缓解但不能消除 |
