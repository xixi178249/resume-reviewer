# resume-expert（对方）↔ resume-reviewer（我们）：对比与互相评价

> 对比对象：<https://github.com/Tissue-for-charlie/resume-expert>（v1.7.0，MIT）
> 对比时间：2026-11-04
> 方法：把对方仓库 clone 到本地逐文件读（`SKILL.md` 733 行、13 份 references 共 5504 行、`test-prompts.json` 8 个用例），与我们仓库的实际代码/测试计数对照。所有数字都是数出来的，不是估计。

---

## 一、一句话结论

**他们把「怎么写好简历」写成了 5500 行的知识库；我们把「怎么证明评得准」写成了 1.6 万行代码和 453 条断言。**

- 论**知识的广度**（行业、职级、格式、本地化 ATS），我们明显落后。
- 论**结论的可信度**（同一份简历评三次是否一致、凭什么这么打分、改完有没有变好），他们没有任何机制，我们有可跑的证明。
- 两者不是同一类产品：他们是**顾问**（会写、会讲、会问），我们是**裁判**（有尺子、有证据链、有复核）。

## 三、逐项对比

### 1. 知识广度：对方胜，而且差距不小

对方 `references/industry-matrix.md` 给了 15 个行业的「关注重点 × 实习/校招/社招」三段策略；`scoring-system.md` 给了**每个行业一套权重**（金融 35/20/25/20、设计 35/30/15/20、演艺五维 30/20/20/10/20…）；`chinese-ats.md` 细到北森对「表格里嵌套表格」会丢数据、英文缩写必须带中文全称。

我们只有一套权重（25/25/20/15/15）。**结果是：投国企和投互联网拿同一把尺**，这在真实使用里是系统性误判——国企看的政治面貌、学历层次，我们不但不给权重，还明确禁止评价（`DISCRIMINATORY` 正则会把「中共党员」标成歧视性信息）。这条我们做对了「不歧视」，但做少了「该行业确实看重什么」。

### 2. 可验证性：我们胜，对方几乎没有

对方的 `SKILL.md` 写着「**保证不同对话中评分一致**」，靠的是 5 档分数段锚点 + 评分前先读 2-3 个 golden case 校准。这是**祈使句**，没有任何机制保证。

我们这边是能跑的东西：

```
$ python scripts/run_tests.py
全部通过：23/23 个套件，453 条断言。
```

包括「同一份输出连跑三次分数差 ≤6」「阈值改了必须三处同步否则测试 FAIL」「同一份简历评三次取中位而非取平均」。对方 8 个 test case 是**提示词**（测模型有没有触发技能），不是断言（测输出对不对）。

### 3. 事实守卫：我们胜在「拦在写入前」

对方有 C1「不虚构」，写得很清楚（"虚构经历在面试 3-4 层追问下必然穿帮"），但它是**散文约束**，靠模型自觉。

我们的守卫是代码：

- `patch_protocol.fact_issues()` 检查 `fabricated_number`（新文里的数字不在原文∪用户手填里 → hard 拦）、`ownership_upgrade`（弱动词升级 → soft 拦）
- `apply_patches()` 在**每次替换之前**跑守卫，hard 直接不进版本
- `check_output.py` 的 `number_audit` 要求简历里每个百分比都追溯到原文

差别在于：**对方只能事后提醒，我们能拒绝写入。**

### 4. 版本与回滚：我们独有

对方模式 C 有一条很实在的教训：「**禁止重跑生成脚本覆盖手动修改**」——因为用户手改的 Word 会被覆盖。但它没有版本机制，只能靠「不要重跑」来防。

我们有 `version_store.py`：正文 sha256 作 doc_id、`parent` 成链、上限 10 版、撤回 = 切回 parent 而不是反向应用补丁、同一份简历再传复用同一条链。

### 5. 低信息 / 弱势背景处理：对方胜

对方的 `low-info-strategies.md`（314 行）专门讲：全维度 ≤4 个时切换批量提问、「深度展开」把一个项目拆 4-6 条 bullet、「技能概要补偿」+「排版补偿」、兼职怎么归类、空窗期/双非/大龄怎么写。

我们是**硬阈值**：正文 <120 字直接拒（`CHAT_NO_TEXT`）。中间态（信息不全但能评）没有策略。

### 6. 行业本地化 ATS：对方胜

我们的 `ats_check` 是 10 项视觉白名单 + 4 项文本层（章节/联系方式/乱码/页数）。对方有国内三大 ATS 平台的解析特点、DOCX 规范（每个 TextRun 显式设 font、超链接用 ExternalHyperlink、GBK 编码坑）、以及「扫描版 PDF 完全失败」这类实操细节。

### 7. 改稿闭环：我们独有

对方模式 C 给改写建议，但**没有「改完有没有变好」的度量**。

我们有 `closure.py`：记录每次 apply 的补丁 → 下次评同一份简历时判断「建议落实率」，可判条数 ≥10 才报数。以及 apply 后**必重评并显式报差**（实测 68 → 60，delta −8，界面直接说「分数掉了，可以直接撤回」）。

### 8. 生成能力：对方独有

他们能从零写出一份 DOCX（含字体、超链接、bullet numbering），还有 5 级回退链（docx-js → python-docx → HTML → LaTeX → Markdown）。

我们刻意不做。理由：生成必然引入编造风险，会直接击穿我们「零编造」这条卖点；而且改稿一旦变成「重新排版一份 docx」，用户手改的内容就会被覆盖——这正是对方踩过并写进 SKILL.md 的坑。

### 9. 透明度：对方胜

对方的规则是 **md 文件**，用户打开就能读、能改、能提 PR。我们的规则一半在 `rubric.yaml`（可读），一半在 `check_output.py`（1200 行 Python，只有开发者读得懂）。

### 10. 真实可用性：我们胜

对方装进 Cursor 才能用，没有界面、没有版本、没有分数对比、没有下载。我们有网页：上传 → 评审 → 一键进改稿工作台 → 逐条采纳 → 自动重评 → 下载 .txt，公网可访问，访客自带 key。

## 四、互相评价

### 4.1 如果对方是审稿人，会怎么评我们（他们说得对的地方）

1. **「你们的尺子只有一把。」** 15 个行业的简历用同一套权重，等于承认自己只对互联网/科技岗调过参。投国企的简历被扣「没有量化成果」——那条在体制内根本不是重点。
2. **「你们的校准数据是零。」** 8 份样本、0 份人工金标，`benchmark.py` 现在只能输出 `NOT_READY`。所有分数都是**未经校准的专业判断**，不是测量。
3. **「你们的规则藏在 Python 里。」** 用户没法审阅你们的评分逻辑，也就没法反驳。我只能读你们 README 的表格。
4. **「你们不能帮他写第一份简历。」** 一个没有简历的人打不开你们的产品。
5. **「你们要求用户自带 API Key。」** 对一个「给室友用」的工具，这是真实的摩擦——他会问「为什么我要去注册 DeepSeek」。

### 4.2 我们评他们（我们认为他们的问题）

1. **「保证不同对话中评分一致」是一句无法验证的承诺。** 75 份手写 golden 允许 ±5，却没有 CI、没有一致性指标、没有人测过同一份简历评两次差多少。写过评分系统的人都知道：**尺子的稳定性不靠分数段描述，靠重复测量的方差。**
2. **C1「不虚构」只有 prose。** 面试预测环节最容易出事——他们要求「基于简历内容预测追问」，但没有任何机制阻止模型把「你应该有 3 段实习」写成「你有 3 段实习」。
3. **零可执行代码意味着零回归保护。** 5504 行 md 里任何一次「优化措辞」都可能悄悄改变判分行为，没有人会发现。我们的 `test_rubric_single_source.py` 就是为了防这件事（prompt 里的阈值和代码里的阈值必须同一个数）。
4. **8 个 test case 测的是「技能有没有被触发」，不是「评得对不对」。** 这两件事差一个数量级。
5. **75 份 golden 是自证的。** 谁写的？和评分规则是同一个人吗？如果 golden 分数是照着规则反推的，那它就是规则的同义反复，不是外部标准。

## 五、我们该抄的五条（已排优先级）

| 优先级 | 抄什么 | 落点 | 成本 |
|---|---|---|---|
| **P0** | **行业权重映射**：把 `rubric.yaml` 扩成 `industries:`（互联网/金融/国企/设计/游戏/政府/教育/医疗…，每行业 4-5 维权重 + 该行业专属硬门槛词表） | `config/rubric.yaml` + `weights_for(industry)` + 报告页显示「按 XX 行业权重」 | 中：权重表要人写，但机制已有 |
| **P1** | **分数段锚点写细**：5 档 + 每档典型特征（我们现在只有 3 个数字 + 一句「为什么不是 64 也不是 75」） | `prompts/system-*.md` 的评分锚点段 | 低 |
| **P1** | **面试预测升级**：`followup_risks` 每条加「会怎么问 / 该准备什么 / 常见翻车点」 | schema + prompt + 报告渲染 | 中 |
| **P2** | **低信息简历策略**：<120 字不直接拒，切「批量提问 + 只给结构建议」模式 | `ingest`/`local_engine` + 前端提示 | 中 |
| **P2** | **同岗位基准对比**：给「同岗位中位数 / 前 25% 门槛」——**但必须标注数据来源**，没数据就不说 | 报告页 | 高（要有数据才敢说） |

## 六、我们不建议抄的三条

1. **75 份手写 golden 的 ±5 允差。** 我们的路线是双人盲评 + κ≥0.6 + MAE≤8，比手写 golden 硬得多。降级成 ±5 等于放弃可信度这条主线。
2. **从零生成简历。** 与「零编造」卖点直接冲突，且会把改稿变成重新排版（他们自己踩过这个坑并写进了 SKILL.md）。
3. **多格式输出链（docx/LaTeX）。** 我们刻意留在文本层：改的是句子，排版交给用户自己的 Word 模板。引入 docx 生成会把「改哪一句」变成「重新生成一份」。

## 七、结论

- **如果用户要的是「帮我从零写一份简历」**：用 resume-expert。它覆盖面广、懂行业、能出文件，我们没有这个能力。
- **如果用户要的是「我这份简历到底行不行、改完有没有变好、凭什么这么说」**：用 resume-reviewer。它会给分数、给证据、给改写、给复核，并且**说不出理由的地方会明说不知道**（`insufficient_data` / `not_ready` / 「请核对原文」）。

我们真正的差距不在代码量，在**知识的广度**（行业 × 职级 × 本地化 ATS）。而他们真正的差距不在知识，在**没有测量**。

下一步最值钱的一件事：把行业权重映射做进 `rubric.yaml`。这一条能把我们「只有一把尺」的短板补掉一半，而且不需要新数据——只需要把行业共识写下来，然后让测试盯着它别漂。
