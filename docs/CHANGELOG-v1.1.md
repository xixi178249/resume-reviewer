# v1.1 改动（2026-10-22）

> 起因：对标 kickresume.com 后，把我们结构性落后的三处补上（详见 `docs/kickresume-对比.md` 第五节）。
> 原则不变：**只做判断，不做代写；不预测通过率；能本地跑就不上云。**

---

## 1. 岗位 JD 匹配（补最大的功能缺口）

**之前**：界面只收"目标岗位"四个字，`case["jd"]` 一直是空字符串。prompt 与 schema 里本来就有 `jd_match`（关键词 / 覆盖率的校验逻辑都写好了），但因为没有输入，模型只能输出 `jd_provided:false`，报告里也从不显示。

**现在**：
- 第二步多了「岗位 JD（可选）」文本框，整段招聘要求直接粘进去；
- 服务端把它塞进 `case["jd"]`，prompt 的 `{{jd}}` 才真正被填上；
- 报告新增一段「岗位匹配（对着你贴的 JD）」：

```
## 岗位匹配（对着你贴的 JD）

**关键词覆盖 62%**：5 个在经历里有证据，3 个没有。

- ✅ Java / Spring Boot：专业技能 + 项目经历
- ✅ MySQL 索引与事务：专业技能 + 慢查询优化 bullet
- ⚠️ Spring Boot：只出现在技能栏，经历里没有证据——面试官会追着问
- ❌ 单元测试：简历里完全没有
```

**和 kickresume 的差异**：它的 Tailoring 帮你把关键词塞进去；我们指出"塞了也没证据"——所以 ⚠️ 和 ❌ 分开报，`stuffed_terms` 由 `check_output` 反向校验（声称有证据就必须原文找得到）。

**命令行**：`python scripts/review.py 简历.pdf --job "后端开发" --jd-file jd.txt`

## 2. 改完的闭环：可粘贴块 + .docx

**之前**：报告只给 `报告.md`，用户改完 3 句话还得自己在简历里找位置。

**现在**：
- 报告里多一段 **「改完的版本（按简历顺序，可直接粘贴）」**，代码块样式；
- 顶部按钮 **「复制改好的段落」**，一次复制三条改写（按 `original` 在原文中的位置排序）；
- 新增 **「下载 .docx」**：服务端用 `python-docx` 把 Markdown 报告转成带标题层级的 Word（标题/引用/项目符号/等宽段落都保留），文件名 = 简历名；
- 新增端点 `GET /api/download?name=<stem>&kind=md|docx|json`，只允许读 `reports/` 目录内的文件（防路径穿越）。

编造数字的过滤逻辑抽成了 `select_rewrites()`，报告的三处改写和可粘贴块共用同一份结果——不会出现"报告里撤下了、粘贴块里还在"。

## 3. 进步可见：最轻量的历史

**之前**：PRD 明确不做历史（理由：恢复成本低于实现成本）。

**现在**：只加了一层，不改定位——
- `reports/.history.json` 记 `{文件名: [{时间, 分数, 档位, 岗位, 是否带 JD}]}`，每份最多 20 条；
- **不存任何简历正文**，只存分数；
- 上传同名文件时，第二步提示「这份简历你评过 2 次，上次 72 分（10-22 13:43，带 JD）」；
- 评完后报告顶部显示「比上次 +9 分」或「与上次同分」；
- 报告结论行也会带 `（比上次 +9）`，导出的 .md/.docx 里同样有。

不做：版本 diff、账号同步、跨设备。要这些就是另一个产品了。

## 4. 顺手修的

| 问题 | 处理 |
|---|---|
| Markdown 代码块在页面上不换行、不保留缩进 | `mdToHtml` 补 `<pre class="code">`，等宽字体 + 自动折行 |
| 第二次评审时，`render()` 无法表达"分数变化" | `render(..., delta=None)` 新参数，CLI/服务端共用 |
| 下载 .md 原先是前端 Blob，文件名固定为「简历评审.md」 | 改走服务端下载，文件名跟随简历名，中文用 `filename*=UTF-8''` 编码 |

## 6. 界面重排（同日，参考 kickresume 的版式语言，但保留我们的克制）

参考的是它的**信息层级**，不是它的营销风（不用插画、不用渐变卡片、不加五颜六色的装饰）。

| 改动 | 之前 | 现在 |
|---|---|---|
| 页面骨架 | 标题 + 两张卡片，没有进度感知 | 顶部固定栏（品牌 + "本地运行，报告不出这台电脑"）+ hero（一句话价值 + 三个事实 chip）+ **三步进度条** |
| 首屏文案 | "上传 PDF / 图片 / Word，给出一页能改的报告" | 大字主张「告诉你**哪一句会让你被筛掉**」+ 一句边界说明（不夸你、也不替你写） |
| 步骤 1 | 两个 tab + 裸拖拽区 | 分段控件（segmented）+ 带图标的拖拽区 + 格式说明 + 选中后的文件 chip + "识别文本大约 1~3 秒"的预期管理 |
| 步骤 2 | 徽章、预览、两个输入框堆在一起 | 卡片头 + 类型/字数徽章 + 上次评审提示 + 带「已脱敏」标签的预览框 + 三个带右侧提示的表单项 |
| 报告 | 直接渲染 Markdown，分数混在标题里 | **顶部分数卡**：大号分数（按档位着色）+ 档位徽章 + 比上次变化 + 三颗状态药丸（初筛/面试/格式）；正文标题左侧加蓝色标志条 |
| 操作区 | 三个按钮裸排 | 五颗按钮固定在报告底部，用分隔线与正文分开 |
| 字体/间距 | 15px / 1.7，卡片 22px 内边距 | 保持字号不变，卡片内边距 24px、圆角 16px、阴影只做一层极浅的投影 |
| 移动端 | 仅收窄内边距 | 步骤条只保留当前步文字、隐藏顶栏右侧说明、分数缩到 36px |

**没动的**：颜色仍只表达状态（绿=过、琥珀=风险、红=不行）；不加图表、不加雷达图；报告正文的文字一个没改。

**验证**：Chrome 无头截图对比 1180px 与 485px（Chrome 最小窗口宽度）两档；`document.scrollWidth === clientWidth`，无横向溢出；`node --check` 通过。
