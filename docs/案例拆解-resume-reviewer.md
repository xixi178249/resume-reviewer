# resume-reviewer 案例拆解

**分类**：AI 求职工具 / 简历评审（B2C，单人使用）
**体验时间**：2026-10-20 ~ 2026-10-21（自研产品，v0.1 → v1.3 全流程亲历）
**拆解人视角**：既是 PM，也是这套东西的实现者

> 说明：本文按通用案例拆解模板写，但**第三节不写"技术方案推测"**。
> 这是自研产品，推测没有意义——直接写实况，反而能暴露真实的设计取舍。

---

## 一、产品背景

### 1.1 用户与场景

目标用户非常具体：**大二、大三找第一份实习的本科生**，不是校招，不是社招。

这个人群有三个特征，决定了产品形态：

| 特征 | 含义 | 对产品的约束 |
|---|---|---|
| 多数没有正式实习经历 | 简历主体是课程项目、竞赛、社团 | 不能用社招标准评，否则全员不及格 |
| 不知道筛选是怎么发生的 | 以为"写详细点"就有用 | 必须解释**为什么**会挂，不能只给分 |
| 决策周期短 | 一份简历投几十家，改一次用一季 | 建议必须能在 30 分钟内落地 |

### 1.2 痛点拆解

不是"不会写简历"，而是三件更具体的事：

1. **不知道标准**——"我这份能过吗"没有客观参照，只能问学长，学长说法互相矛盾。
2. **没人给具体改法**——所有人都在说"要量化"，但没人告诉他"你这一句该怎么改成什么"。
3. **改完没人验**——改完自我感觉良好，投出去石沉大海，得不到任何反馈。

### 1.3 竞品空白

| 现有方案 | 提供了什么 | 缺什么 |
|---|---|---|
| 通用大模型（直接问 ChatGPT） | 语气友好、结构完整 | 全是"建议加强量化"这类**礼貌的空话**，且会**擅自编造数字** |
| 简历模板站（超级简历等） | 排版、格式、范例 | 只管形式不管判断，不知道你这份能不能过 |
| 付费简历修改（¥200~800/次） | 真人判断，质量高 | 贵、慢、不可复用，且改完仍无人验证 |
| 学长学姐/辅导员 | 经验、人情 | 样本量 1，标准不稳定 |

**空白点很明确**：没有人把"哪些话会在初筛被划掉"变成**可重复、可验证、逐句可执行**的产出。

### 1.4 一句话定位

> 不是"帮你写简历"，是**告诉你哪一句会挂，以及换成什么能过**。

## 二、核心功能拆解

### 2.1 主流程

```
简历(docx/pdf/截图)
   │
   ▼
提取 + 脱敏 ──► 渲染 prompt（规则 + 岗位 + 简历 + 高质量样例）
   │
   ▼
模型输出结构化 JSON（17 个必填字段）
   │
   ├─► 结构校验：字段齐全？分数与 verdict 自洽？
   ├─► 事实校验：每条 evidence 是否逐字出自简历？改写有没有凭空造数字？
   └─► 规则校验：两关公式对不对？展示力问题漏没漏报？动作优先级对不对？
   │
   ▼
用户拿到：结论 + 证据 + 改写 + 追问风险 + 今日动作
```

### 2.2 两道关（这是产品的核心判断模型）

大厂筛简历分两道关，**淘汰原因完全不同**，混在一起评就会给错建议：

| 关卡 | 谁在筛 | 看什么 | 时间 |
|---|---|---|---|
| 第一关 | HR 初筛 | 岗位匹配度 + 有没有硬伤 | 15~30 秒 |
| 第二关 | 业务面试官 | 这段经历经不经得起三层追问 | 3~5 分钟 |

产品的一个关键设计：**两关的通过与否是公式推导的，不是模型凭感觉填的**。

```
gate_hr.pass        = (无硬伤)           且 role_fit ≥ 3 且 impact ≥ 2
gate_interview.pass = evidence_quality ≥ 3 且 高风险追问 ≤ 1
```

### 2.3 七个检验 → 五个维度的映射

| 检验 | 判什么 | 映射维度 | 权重 |
|---|---|---|---|
| 1 三秒测试 | 整份简历 3 秒能不能看出投什么岗、最强点 | structure | 15% |
| 2 单句可读性 | 单句 >40 字 / 2 个以上从句 | structure | — |
| 3 岗位替换 | 换个岗位名是否照样读得通 | role_fit | 25% |
| 4 三层追问 | 能不能答出"为什么这么做" | evidence_quality | 20% |
| 5 "所以呢" | 有动作没结果 | impact | 25% |
| 6 数字溯源 | 简历里**已有**的数字，来源说不说得清 | impact | — |
| 7 展示力 | 弱动词 / 结果前置 / 自评词 / 主线 | structure + competitiveness | 15% |

> 权重 25/25/20/15/15 是**经验值，未做数据校准**。这一点在产品内部被反复标注，不许当结论用。

### 2.4 三个"别人没有"的设计

**① 证据强制：每条意见必须逐字引用原文**

输出的每一条问题都带 `evidence` 字段，且必须能在简历原文里逐字找到。找不到 → 判定为编造 → 直接报错。

这一条的作用不是"更准"，是**让"AI 瞎评"有可被机器抓住的痕迹**。没有它，你无法区分"它真的读了简历"和"它在根据岗位名编"。

**② 数字溯源：反过来查简历里已有的数字**

这是产品和"普通 AI 改简历"最大的分野。

普通工具只会说"要多写数字"。但我们发现，用户简历里的数字**本身就有风险**：

> 面试官会问：这个 87% 是怎么算的？评估集多少条？谁判的对错？

所以产品会逐个审计简历里的百分比，判断"分子分母说不说得清""是自己测的还是估的""有没有第三方验证"。答不清的，标成**隐性炸弹**，并给出面试官的原话追问。

> 实测案例：一份写得很不错的 Agent 算法简历（78 分），两个高分数字（87% 准确率、51% 显存对比）来源都说不清。
> 这不是"写得不够量化"，是**面试会被当场问穿**。前者是优化项，后者是生死项。

**③ 展示力检验：纯文本就能判的"包装能力"**

命题是「简历展示也是一种能力」——同样的经历，会不会展示，结果差一个量级。

四条判定全部可以机械执行：

| 检验 | 判定 | 反例 |
|---|---|---|
| 弱动词且无结果 | 行首是"参与/负责/协助…"**且整行无数字无变化** | `负责商品模块，编写了相关接口` |
| 结果被埋 | 句首 12 字内没有结果信号，结果只说在句末 | `通过调研…经过多次讨论…最终提升了转化` |
| 自评词 | 精通 / 熟练掌握 / 责任心强 / 抗压 | `精通 Java` （无任何证据） |
| 主线 | 读完能不能用一个标签记住这个人 | 只能说"一个还不错的 CS 学生" |

### 2.5 功能边界（明确不做什么）

| 不做 | 原因 |
|---|---|
| 不编造任何数字 | 编了面试一问就崩，**比不优化更严重**。缺的一律用 `[待补充：…]` 占位 |
| 不评价照片/性别/年龄/籍贯/学校层次/专业冷热 | 与投递决策无关，且涉及歧视 |
| 没给截图就不评排版 | 纯文本下"看见"排版就是幻觉，会被脚本判错 |
| 不做"通用简历评审" | 不针对岗位的评审，等于没评 |
| 不做网页 | 室友每周会不会用第二次还没验证，先别做前端 |

## 三、技术方案（实况，非推测）

### 3.1 架构

```
prompts/system-vX.md ──┐
prompts/output-schema-vX.json ──┤
prompts/example-output-vX-good.json ──┴─► build_prompt() ──► build_messages()
                                                              │  (可选：附截图 image_url)
                                                              ▼
                                                        OpenAI 兼容 API
                                                              │
                                                              ▼
                        ┌───────────── check_output.check() ─────────────┐
                        │  结构：字段/量表/分数自洽/verdict 一致          │
                        │  事实：evidence 逐字命中 / 改写无新增数字       │
                        │  规则：两关公式 / 展示力覆盖 / 优先级 / 溯源覆盖│
                        └───────────────────┬───────────────────────────┘
                                            ▼
                                输出 + 批量指标（6 项）
```

零第三方运行时依赖：只用 `urllib` + `json` + `re`。`python-docx` / `pypdf` 仅在提取阶段需要。

### 3.2 三个关键工程决策

**决策一：把规则外置到脚本，而不是堆在 prompt 里**

开发中定下一条原则：

> **凡是能写成脚本的，就不写进 prompt；凡是能写成断言的，就不靠模型自觉。**

结果：prompt 里只留判断标准，可机械验证的部分（引用是否原文、数字是否新增、分数是否自洽、优先级是否正确）全部交给 `check_output.py`。prompt 的自检清单从 7 条砍到 3 条，只留脚本查不了的。

**决策二：用 `schema_version` 区分规则集**

v1.0 ~ v1.3 四套规则同时存在，靠一个顶层字段分流。好处是**可以 A/B 对比**，坏处是要维护向后兼容（实测 v1.0/v1.1/v1.2 旧样例在 v1.3 校验器下仍全部通过）。

**决策三：双层测试——校验器 + 接线**

这是 v1.3 补的最重要一课。

| 层 | 测什么 | 数量 |
|---|---|---|
| 校验器自检 | 给定的坏输出，能不能被抓出来 | 23 项 |
| 端到端接线 | **真正送给模型的东西**对不对 | 23 项 |

为什么必须两层：v1.2 有三个 bug（`--image` 只改标志不传图、few-shot 从没拼进 prompt、schema 必填字段 prompt 里没写），**第一层全都测不出来**——因为它们不在"校验输出"这一侧，而在"组装输入"那一侧。

### 3.3 迭代中的三个真实教训

| 版本 | 犯了什么错 | 修法与验证 |
|---|---|---|
| v1.0 → v1.1 | **规则互斥**：禁止评"照片/性别"，但 schema 又要求写"排版解析失败" | 拆成「歧视性信息禁止评分」+「排版工程信息必须评」两类 |
| v1.1 | **校验器误报**：把"初筛只扫加粗标题"这类元叙述当成"声称看见加粗" | 从词表删掉「加粗/字体」，并在代码里写明为什么不能收录 |
| v1.2 → v1.3 | **实现与设计脱节**：功能写了但没接上（三个 P0） | 新增接线测试；用 v1.2 回归验证——**13/18，5 项 FAIL** |

> 第三条最值得记：**校验器太松等于没有，太紧会逼模型说假话。**
> 误报一次，模型下次就不敢提真问题——这比漏报更隐蔽。

### 3.4 实测数据（v1.3，4 份脱敏样本）

| 指标 | 目标 | 实测 |
|---|---|---|
| 引用命中率 | ≥ 0.95 | 1.0 |
| 编造数字 | 0 | 0 |
| 无图却谈排版 | 0 | 0 |
| 展示力漏报 | 0 | 0 |
| 与人工分 MAE | ≤ 10 | 2.0（**不可信，见下**） |
| 校验器自检 | 全通过 | 23/23 |
| 接线测试 | 全通过 | 23/23 |

### 3.5 成本

| 项 | 数值 |
|---|---|
| prompt 模板 | 7.3k 字符 |
| 注入 few-shot 后 | 16.2k 字符（样例占 55%） |
| 单份简历 token | 约 8k 输入 |
| 运行依赖 | 无（纯标准库） |

样例占比过半是有代价的（模型可能照抄样例而不是遵守规则），所以接线测试里加了一条硬断言：**样例占比必须 < 60%**，并提供了 `--no-example` 开关做对照。

## 四、商业模式

### 4.1 现状：没有，而且现在不该有

诚实地说，这个产品目前**没有任何商业模式**，也不建议现在设计。

原因很简单：**它还没有被验证过**。

> 判据只有一条：**室友会不会在投第二家公司时自己回来用。**
> 他要是每次都要你催，那这不是产品，是个脚本。

在单用户留存都没验证之前谈变现，是在给不存在的用户设计定价。

### 4.2 四条候选路径及代价

| 路径 | 怎么收钱 | 代价 | 适配度 |
|---|---|---|---|
| **订阅制** | ¥9.9/次 或 ¥29/月 | 需要支付、客服、退款；用户是一次性需求，复购差 | 低 |
| **导流分成** | 简历模板站 / 简历精修 / 内推平台买量 | 变现即变质——推荐逻辑会被出价绑架 | 中 |
| **B 端（高校就业中心 / 训练营）** | 按席位或按年 | 销售周期长、要资质、要私有化部署 | **高** |
| **开源 + 口碑** | 不直接变现 | 无收入，但能换工作机会和信任 | **最适合当前阶段** |

### 4.3 我的判断

**短期这不是一门生意，是一件"口碑资产"。**

理由：目标用户（找第一份实习的学生）付费能力最弱、需求最一次性、决策最看免费。硬做 C 端变现，只会把产品做成"付费才能看报告"的样子，反而毁掉它最有价值的部分——**敢说实话**。

真正可能有商业价值的，是**中间那层东西**：权重、检验项、评测集。它本质上是一个"简历质量的标注规范"。这套规范对高校就业中心、训练营、招聘平台是有价值的 B 端资产。

> 所以路径是：C 端免费打磨规范 → 用规范撬 B 端。而不是反过来。

## 五、PM 视角的启示

### ① 这个产品的护城河不是模型，是评测集

换任何一个模型，这套东西的效果不会差太多。但**那 4 份带人工分的样本、那 37 条断言**，是别人拿不走的。

推论：做 AI 产品，"接哪个模型"是最不值得纠结的决策；"怎么判断它做得对不对"才是。

### ② 用户要的不是"评分"，是"能改的那一句"

我们试过只给五维雷达图和总分。结果是：用户看完点头，然后什么都没改。

真正让人动手的是这个：

> 原文：`完成了主要功能，项目可以正常使用`
> 改成：`跑通 [待补充：核心流程] 全流程，用 [待补充：测试方式] 验证，[待补充：使用人数]`

**评分是给产品自己看的，改写才是给用户看的。**

### ③ AI 产品最大的风险不是答错，是"自信地编造"

这类产品的失败模式很特殊：模型说得头头是道，用户信了，然后**在面试现场崩掉**。

所以整个产品有三分之一的设计在防这一件事：
- 每条意见必须引用原文（防瞎评）
- 改写禁止新增数字（防编造）
- 简历里已有的数字也要溯源（防用户自己踩雷）
- 没截图不许评排版（防视觉幻觉）

### ④ 校验器会误报，而误报比漏报更伤

v1.1 里，我们把"加粗"写进了"无图谈排版"的词表。结果模型解释"HR 只扫加粗标题"被误判为幻觉。

**一次误报的代价，是模型从此不敢提真问题。** 这比漏报隐蔽得多——你看不到它，只能看到产出变平庸。

推论：规则不是越多越好，**每条规则都要问"会不会误伤正常表达"**。

### ⑤ 需求验证的最小单位是"同一份简历评三次"

不需要做出来给人看。找三份真简历，自己先当面试官评一遍，再让 AI 评一遍，对照差在哪——**半天就能知道这事靠不靠谱**。

我们绕了一圈才回到这一步，其实它该是第一天的动作。

### ⑥ 凡是能写成断言的，别指望模型自觉

这条既是工程原则，也是产品原则。

prompt 里写"请务必检查分数是否自洽"，模型有相当概率不检查。写成脚本断言，它就必须自洽，否则输出被拒。

**把"要求"翻译成"约束"，是 AI 产品设计里最被低估的一项技能。**

## 六、局限与下一步

### 已知局限（不许当成绩）

| 局限 | 说明 |
|---|---|
| **权重未校准** | 25/25/20/15/15 是拍的，`WEIGHTS` 是唯一真源，改它要同时改脚本 |
| **MAE 2.0 不可信** | mock 剧本先于权重写，属于自我实现。真实校准需要 20 份人工标注 |
| **没跑过真实业务数据** | 所有结论来自 4 份自造样本，模型真实表现未知 |
| **多模态未实测** | 带图评审的 payload 结构有测试，但没真调过带图接口 |
| **只有技术岗** | 产品/运营岗的锚点是空白，虽然 prompt 要求标注，但标准本身没写 |

### 下一步（按优先级）

1. **贴 3 份真实简历跑一次真模型**，看 `evidence_hit_rate` 掉多少——那才是 prompt 的真实水平
2. **攒 20 份人工标注**，做权重回归，MAE 才有意义
3. 加「**补位建议**」模块：没实习经历的人，怎么用课程项目/竞赛/开源补出有效经历
4. 别做网页。先确认室友每周真的会用第二次。
